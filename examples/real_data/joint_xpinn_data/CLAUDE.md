## What this workspace is

`/Users/jiapchen/Research/Data` is a research **data** directory, not a single software project: most top-level folders (`MEaSURES-ice-vel/`, `BedMachineAntarctica-v3.nc`, `Antarctic-boundaries/`, `Kittel2020-SMBAntactica/`, etc.) are independent downloaded/derived Antarctic glaciology datasets with no code of their own. ## Architecture

### File layout

```
joint_xpinn_data/
├── build_dataset.py, config.py, contracts.py, domain.py, resample.py   # core pipeline
├── data_sources/        # velocity/thickness/surface/grounding-line/calving-front providers
├── checks/              # consistency-check registry (see below)
├── utils/               # raster_utils, geometry_utils, color_utils, basin_partition (experimental)
├── diagnostics/         # plot_validation, compare_sources, checks (CLI), plot_basins — standalone CLIs
├── configs/             # one YAML per ice-shelf/grounding-zone build
└── output/
    ├── <ice_shelf>_<grounding_zone>_<buffer_km>km/   # one config's .mat + figures/
    └── basins/                                        # shelf-wide/global basin diagnostics (not config-scoped)
```

### The target output format is fixed, not designed from scratch — with one deliberate exception

`build_dataset.py` must produce a `.mat` file matching the exact field layout DIFFICE_jax's synthetic ISSM data uses (see `/Users/jiapchen/Software/DIFFICE_jax/examples/synthetic_data/data-README.md` and the generator at `/Users/jiapchen/Research/PinningPointInversion/Scripts/Synthetic/+ProcessSyntheticData/process.m`, which is the MATLAB reference implementation this package's Python pipeline mirrors field-for-field). Two regions (grounded grounding-zone, floating shelf), each a cell in `xd/yd/ud/vd/xd_h/yd_h/hd/xd_s/yd_s/sd/h_dense/s_dense/xcol/ycol/xdir/ydir/udir/vdir/xct/yct/nnct/mud/alpha2d/ols_d`, plus bookkeeping (`Xe/Ye/Xe_h/Ye_h/idxcrop/idxcrop_h/basal_mask/region_labels/region_masks/options/expected_save_variables`). `mud`/`alpha2d` (viscosity, basal friction) are intentionally NaN — for real data these are inversion *targets*, not observations, unlike the synthetic case where they're ISSM ground truth.

`xd_s`/`yd_s` are the one addition to DIFFICE_jax's original schema: surface elevation (`sd`) is sourced independently of thickness rather than resampled onto `xd_h`/`yd_h`, so it needs its own coordinates. This means the pipeline's output is **not yet consumable by DIFFICE_jax's training code as-is** — see `docs/adr/0001-surface-elevation-independent-coordinates.md` for why, and what would need to change on the DIFFICE_jax side to accept it.

### Two-layer design, applied twice: contracts vs. providers, and checks vs. their registry

Every data kind has a fixed output **contract** (`contracts.py`): `PointObservations` (x, y, `values` dict, optional per-point uncertainty `weight`) for velocity/thickness/surface, `Geometry` (list of point-array segments, optional per-segment `normals`) for grounding line/calving front. Downstream code (`domain.py`, `build_dataset.py`) only ever depends on these shapes.

Each data kind then has a **registry of provider functions** in `data_sources/`, one per real source, each free to have completely different internal logic (grid CNT-masking vs. CSV sentinel-filtering-plus-reprojection vs. mask-pixel-adjacency) as long as it returns the right contract:
- `velocity.py` → `VELOCITY_SOURCES` (`measures_v2`, `custom_xy`)
- `thickness.py` → `THICKNESS_SOURCES` (`bedmachine_v3`, `bedmap1_csv`, `bedmap2_csv`, `concat`, `custom_xy`) — one source per config (`PipelineConfig.thickness_source`), from which `build_dataset` derives both output *roles*: `h_dense` (resampled onto the velocity grid) and `hd`/`xd_h`/`yd_h` (the source's own native points; resampled onto the velocity grid too for a dense grid like `bedmachine_v3`, which has no distinct native sparse points). `bedmap1_csv`/`bedmap2_csv` share a column schema (`process_bedmap_column`, `_read_bedmap_csv`) since both are BEDMAP-series CSV exports. `concat` merges multiple named sources of this kind into one `PointObservations` (`sources: [{source: ..., kwargs: {...}}, ...]` in its kwargs) — e.g. the Amery configs combine BEDMAP1 (1966-2000) with BEDMAP2's BGR PCMEGA survey (2002-2003) for thickness, since neither alone covers the Lambert/Mellor/Fisher area as densely as the two together.
- `surface.py` → `SURFACE_SOURCES` (`bedmachine_v3`, `bedmap1_csv`, `custom_xy`) — one `PipelineConfig.surface_source` feeding both surface roles (`s_dense`/`sd`) the same way thickness does, but a fully independent data kind, not derived from thickness even where a provider happens to read it from the same file (see CONTEXT.md's "Surface elevation")
- `grounding_line.py` → `GL_SOURCES` (`measures_boundaries_2008` default, `bedmachine_mask`, `custom_xy`)
- `calving_front.py` → `FRONT_SOURCES` (`bedmachine_mask` default, `antarctic_boundaries_mask`, `velocity_mask`, `measures_boundaries_2008`, `custom_xy`)

`boundaries.py` (named basin/ice-shelf polygon lookup) is deliberately *not* part of this plugin system — it's stable infrastructure for "roughly where is `<name>`", not something swapped per run. It had a real bug (now fixed): the `.mat` polygons encode interior holes (ice rises/rock outcrops) via ESRI ring-winding convention (exterior clockwise, holes counter-clockwise) — treating every ring as solid fill silently inflates shelf/basin area.

`utils/raster_utils.py` and `utils/geometry_utils.py` hold the generic array/geometry math (pixel-neighbor adjacency, ring winding, circular run-finding) shared across providers that would otherwise be duplicated per mask source.

The same contract-vs-registry shape is used a second time for **how far the floating region extends** beyond the grounded corridor: `floating_region.py` → `FLOATING_REGION_SOURCES` (`whole_shelf` default — the named shelf's full extent, independent of `buffer_km`/`grounding_zone`, exactly today's only prior behavior; `flowline_corridor` and `basin_partition` restrict it to a corridor around one grounding zone's own flow, for a shelf fed by many tributaries where the whole-shelf default would include hundreds of km of unrelated ice — see `utils/basin_partition.py`, whose forward-streamline-tracing machinery both reuse unmodified). `PipelineConfig.floating_region_source`/`floating_region_kwargs` select it, same pattern as every other `*_source`/`*_kwargs` pair. Every registered function returns `(polygon, front_reference_points)`, not just a polygon — see `domain.py`'s pipeline-order section below for why `_trim_front_to_region` needs the latter. `flowline_corridor`'s own buffer radius optionally tapers with downstream arc-length distance from the grounding line (`min_margin_km` → `margin_km` over `taper_km`, via a smoothstep — see `taper_margins_m`), or, with `taper_km=0`, is a flat `margin_km` giving a constant-width corridor (Byrd/Ross East uses the latter: a uniform 8km, since its traced streamlines are a coherent bundle and a wider tapered buffer bulged far enough downstream to hit the shelf boundary and kink — see `HANDOFF.md`). Its `min_normal_velocity_myr` is derived automatically from `region_strategy_kwargs.min_speed_myr` when `region_strategy="flow_restricted"` (see below), so the two can't drift out of sync the way a hand-set duplicate value could.

A third time for **which shelf-class builds the grounded/floating geometry**: `domain.py` → `REGION_STRATEGIES` (`"simple"` default — no GL flow-filtering, no velocity-thresholded grounded corridor, the common case; `"flow_restricted"` opts into both, via `PipelineConfig.region_strategy`/`region_strategy_kwargs`). Every registered function takes `(config, basin_raw, shelf_raw, gl, grounded_polygon, **region_strategy_kwargs)` and returns a `RegionShape` (grounded/floating polygons, the final `gl`, whichever basin polygon the shared epilogue should see, optional front reference points) — see the pipeline-order section below for exactly where this seam sits and `docs/adr/0002-shelf-class-region-strategy-registry.md` for why the grounded/GL half of shelf-class variation needed the same treatment the floating half already had. `process_simple`'s body references none of the flow-filtering/corridor/smoothing helpers `process_flow_restricted` uses — a shelf on the default path structurally cannot execute Byrd-class geometry, rather than merely not triggering an `if` branch that happens to live in the same function.

And a fourth time for **consistency checks**: every check function in `checks/` takes `(config, regions, **kwargs)` and returns a `CheckResult` (`contracts.py` — name, region, per-point `x`/`y`/signed `metric`, `unit`, optional `threshold`/`passed`), registered in `checks.CHECKS`. `checks/velocity_front.py` (`velocity_vs_front`) and `checks/hydrostatic.py` (`hydrostatic_equilibrium`) are the two entries today. See CONTEXT.md's "Consistency check" for what distinguishes this from a code-correctness test — `joint_xpinn_data/tests/regression_baseline.py` is the one test of that kind that exists today (a frozen-output regression check for the "simple"-strategy reference configs, not a per-shelf physical-consistency judgement).

### Adding a new source, a new check, or a new ice-shelf/grounding-zone

New source: write one function matching its kind's contract, add one entry to the relevant `*_SOURCES` dict. No existing function or shared pipeline code changes.

New check: write one function taking `(config, regions, **kwargs)` returning a `CheckResult`, add one entry to `checks.CHECKS`, add a subcommand in `diagnostics/checks.py`'s CLI.

New shelf/zone: add a YAML file under `joint_xpinn_data/configs/` setting `ice_shelf`, `grounding_zone`, `buffer_km` (see `configs/TEMPLATE.yaml`) — the basin/shelf names must match exactly what's in `Antarctic-boundaries/data/{basins_refined_v2,iceshelves_2008_v2}.mat` (use `boundaries.list_names(...)` to check spelling). `config.load_config` turns a YAML file into a `PipelineConfig`; `python -m joint_xpinn_data.build_dataset <file-or-dir>` builds one config or every `*.yaml` in a directory.

### Pipeline order (`domain.py` → `build_dataset.py`)

`build_regions` starts from `basin_polygon`/`shelf_polygon` completely raw (unsmoothed) — deliberately: GL sources like `measures_boundaries_2008` select points by real distance to `basin_polygon`'s own boundary ring (see below), and `basin_partition.flux_gate_seeds`/traced streamlines terminate against `shelf_polygon`'s real edge. Smoothing either polygon before those steps run changes their answers unpredictably (confirmed both ways for Byrd — see HANDOFF.md's sharp-edge investigation). Smoothing only ever happens *after* the fact, applied to `grounded_polygon`/`floating_polygon` themselves, once everything that needed the true boundary has already used it — see below for exactly where.

`build_regions` buffers the grounding line's raw points into a corridor (a `MultiPoint` buffer, not an ordered `LineString` — some GL sources return unordered pixel scatters, and point-buffering ≈ line-buffering when point spacing ≪ `buffer_km`; the buffer is huge relative to a GL source's own stray tail points, so building it from the untrimmed grounding line here doesn't meaningfully change its shape), intersects with the basin to get `grounded_polygon` (`_buffer_grounded`, a module-level function called once here as a bootstrap and again inside `process_flow_restricted` to re-buffer from a narrowed `gl` — same function, not duplicated logic). `_buffer_grounded` also closes the result with a small (`_GROUNDED_POLYGON_SMOOTHING_M=2000m`) buffer-out-then-in before returning it — `basin_polygon` (`basins_refined_v2.mat`) and `shelf_polygon` (`iceshelves_2008_v2.mat`) are independently digitized and cross each other repeatedly over short spans near the coast rather than along one clean shared arc, which otherwise carves spurious sub-2km-scale notches/holes into `shelf_polygon.difference(grounded_polygon)` that have nothing to do with real geography (confirmed for Byrd — see the floating-region paragraph below).

Next, `_trim_gl_to_interface` against the *cheap* `shelf_polygon.difference(grounded_polygon)` (not a `floating_region_source` restriction — the true grounded/floating interface doesn't depend on how far the floating region ends up extending downstream, and empirically the real narrowing work is done by `process_flow_restricted`'s flow filter below regardless of which floating polygon this trim uses, so there's no reason to pay for an expensive corridor trace just for this bootstrap). This keeps only GL points actually near where the two regions touch — a GL source's own inclusion criterion doesn't know about the ice-shelf polygon at all (e.g. the default `measures_boundaries_2008` keeps continental points within `tol_km` of the *basin's entire boundary ring*, which includes lateral basin walls shared with neighboring basins/rock — confirmed for Amery: per-point distance to the true shared boundary is ~0m through the middle of each raw segment, then jumps straight to several km at both tail ends). Ordered sources are trimmed by contiguous run (drop the tails, keep the middle); unordered sources are filtered pointwise.

This is the seam: everything up to here (raw polygon load, GL load, the bootstrap buffer/trim above) and everything from the floating-region load onward (front load/trim, normals, velocity reconciliation, cut-boundary computation, `DomainRegions` assembly) is shared, shelf-class-independent code in `build_regions` itself. In between, `build_regions` dispatches to `REGION_STRATEGIES[config.region_strategy]` — `process_simple` (default) does nothing more before handing `grounded_polygon`/`gl` straight to the floating-region load below; `process_flow_restricted` (opt-in) does everything in the next two paragraphs first. See `docs/adr/0002-shelf-class-region-strategy-registry.md`.

Inside `process_flow_restricted`, `_filter_gl_by_flow` drops GL points where real velocity (sampled via `utils/basin_partition.velocity_field`) is at or below `region_strategy_kwargs.min_speed_myr` — a basin's geometric interface with a shelf can be wider than just the named glacier's fast trunk (confirmed for Byrd: a single contiguous ~76km-wide interface spanning real speeds 2-832 m/yr, median only 170; `min_speed_myr=500.0` isolates a single ~20km segment matching Byrd's known confluence width). Same ordered/unordered run-vs-pointwise split as `_trim_gl_to_interface`. `grounded_polygon` is then re-buffered from this narrower `gl` (`_buffer_grounded` again) so it stays consistent with it — otherwise it can end up far wider than the flow-consistent floating corridor it meets at the interface (confirmed for Byrd: `buffer_km=100` is generous enough that `basin_polygon`'s own broad shape near the coast, not `gl`'s width, dominates the intersection either way — re-buffering alone left `grounded_polygon` unchanged at ~100-140km wide). A local `basin_polygon` variable is also reassigned to a smoothed version here (`_smooth_near_interface`, referencing raw `shelf_polygon`) — safe now that `gl`'s real fast-trunk interface was already identified using the raw one above — so this second `_buffer_grounded` call, and `_grounded_corridor` below, both see the smoothed shape instead of `basin_polygon`'s own real coastline detail; this smoothed basin is also what `RegionShape.basin_polygon` reports back to `build_regions`' shared epilogue, so the calving-front load and velocity reconciliation see it too. This smoothing call (and the matching one for `floating_polygon`, done in the shared epilogue — see below) also passes `protect_points=gl.all_points()`, `protect_radius_m=_GL_PROTECTION_RADIUS_M=10000m` — closing has no notion of "the real interface must stay exactly here," so without protection it can (and, confirmed for Byrd, did) shift the boundary 13-26km away from the real reported `gl`, off of a real concave feature of `basin_polygon` that the true GL happens to sit on. `_smooth_near_interface` excludes this radius around every GL point from the smoothing zone entirely, so that segment of the boundary is always returned exactly as-is regardless of `radius_m`/`interface_extent_m` — confirmed this brings `gl`-to-region-boundary distance down to ~2-123m (matching real data resolution) while still comfortably clear of the ~30-40km-away mismatch the smoothing exists to fix.

If `region_strategy_kwargs.corridor_margin_km` is *also* set, `_grounded_corridor` further narrows `grounded_polygon`: it builds a stadium/capsule shape (a `LineString`, centered on the GL points and oriented along real mean velocity direction, buffered by half the GL's own across-flow width plus `corridor_margin_km`) purely to set a search area, length cutoff (`length_km`), and orientation — not as a hard edge. Within that stadium's bounds it traces the `min_speed_myr` (the same value used for the GL filter above) contour of real, Gaussian-smoothed (`smooth_km=3.0`) velocity magnitude via `utils.raster_utils.polygon_from_level_set` (marching squares), pads the result out by `lateral_margin_km`, and intersects with the stadium for the length cutoff. Two earlier, less smooth approaches were tried and replaced in turn: an oriented *rectangle* (`shapely.box` + rotate/translate) showed hard 90°-corner artifacts once built into a real domain — replaced by the stadium; the stadium alone, used as a hard intersection boundary, still let `basin_polygon`'s own real coastline detail become the grounded region's visible edge wherever the stadium was wider than it — replaced by using the stadium only to bound a velocity-thresholded contour instead. Marching squares was chosen deliberately over rasterizing a mask to a polygon (`rasterio.features.shapes`-style): a rasterized mask's boundary is blocky at pixel resolution regardless of how smooth the underlying field is, while marching squares linearly interpolates the crossing point within each grid cell, giving a genuinely smooth contour from a smooth field.

If `config.grounding_line_resample_m` is set, the (trimmed, possibly flow-filtered) grounding line is then resampled to that even arc-length spacing (`utils/geometry_utils.resample_geometry`) — all three Amery configs and Ross East/Byrd set this to `500.0`. Both `process_simple` and `process_flow_restricted` apply this same optional step, at the point in each where their own GL is otherwise final. Resampling assumes an ordered polyline (`Geometry.ordered=True`, true for `measures_boundaries_2008`); for an unordered mask-pixel-adjacency source (`bedmachine_mask`, `ordered=False`), it emits a loud warning and falls back to sorting points counterclockwise around their centroid (`order_counterclockwise`) — a heuristic, not a real boundary reconstruction. This is what flows through everywhere downstream: the calving front load (which needs it for GL-exclusion when `calving_front_source="measures_boundaries_2008"`), the grounded region's "cut boundary" (the arbitrary buffer edge, where a data-driven Dirichlet BC is appropriate — *not* the grounding line, which is a real physical interface reported separately via `x_md/y_md`), `ols_d`, and the reported `x_md`/`y_md` themselves.

Each strategy then calls `floating_region.load_floating_region`, using the *raw* `shelf_polygon` (see above for why) and its own final `grounded_polygon` — it returns `(floating_polygon, front_reference_points)`, the real (possibly restricted) floating region plus a strategy-specific tight reference for where the true calving front should be (only `flowline_corridor` provides one today: each traced streamline's own last recorded point, exactly where it left the shelf polygon; `None` for `whole_shelf`/`basin_partition`). `process_flow_restricted` derives this call's `floating_region_kwargs.min_normal_velocity_myr` from its own `min_speed_myr` (via `dataclasses.replace`, `setdefault` so an explicit override still wins) rather than requiring it hand-set separately — see the floating-region paragraph above for why a mismatched value here matters. Inside `flowline_corridor`, `floating_region.taper_margins_m` sets each traced point's own buffer radius: `min_margin_km` (a core that sits strictly around the flow lines themselves) plus a band that ramps via a smoothstep (`3t²-2t³`, zero-derivative at both ends so it eases in near the GL and reaches a true plateau at `margin_km` by `distance=taper_km`) — or a flat `margin_km` everywhere when `taper_km=0` (a constant-width corridor, what Byrd uses). Note the taper only shapes the buffer radius over the first `taper_km` from the GL; it does not control the corridor's downstream width once at plateau, nor where the buffer envelope meets the shelf boundary (that intersection, at a wide margin, was the real cause of Byrd's "end of widening" kink — fixed by the uniform narrow corridor, not by the taper profile — see `HANDOFF.md`). `load_floating_region` then runs every strategy's raw result through two cleanup passes: `_clean_floating_polygon` (a small, sub-3km closing plus keeping only the dominant connected component — fixes corridor-construction-scale noise, e.g. a 4.2 km² island splitting off right where the taper radius is tightest) and, back in `build_regions`' shared epilogue, `_smooth_near_interface` referencing raw `basin_polygon` (a larger, ~20km closing restricted to within 60km of `basin_polygon` — fixes the same basin/shelf digitization mismatch at the larger scale described above, applied to the *result* rather than to `shelf_polygon` beforehand for the same reason `basin_polygon` isn't smoothed before GL loading). This epilogue smoothing runs unconditionally for every `RegionShape` a strategy returns — confirmed non-trivial for Amery's `process_simple` output too, not just Byrd's, when this was momentarily scoped as Byrd-only during the `region_strategy` refactor (caught by `joint_xpinn_data/tests/regression_baseline.py`, not by inspection). Its GL protection, though, *is* conditional: `protect_radius_m=_GL_PROTECTION_RADIUS_M` for `simple` (no clip, so the closing must be kept off the real GL to preserve alignment), but `protect_radius_m=0` when a strategy supplies an `interface_halfplane` — the clip re-imposes GL alignment exactly, so the protection is redundant there, and its carve-out otherwise leaves a thin (~2km) notch where the protected raw zone abuts the smoothed zone (confirmed for Byrd, ~8km from the GL; dropping it removes the notch, keeps alignment at ~11m mean, and — as a bonus — eliminates the sub-0.03 km² sliver holes the carve-out also created). Real, large-scale fragmentation (this basin's flow genuinely splitting into separate lobes downstream) is caught first by `_warn_if_corridor_looks_broken`, which runs on the pre-cleanup result, before either cleanup pass silently keeps only the dominant piece.

`build_regions` then resolves the grounded/floating overlap — both regions can spill across the grounding line (the grounded capsule extends downstream of it; `_smooth_near_interface`, being inflationary, regrows `floating_polygon` upstream into it), so the same location would otherwise be reported as both grounded and floating velocity — confirmed for Byrd, a ~216 km² overlap lens straddling the GL. How it resolves depends on whether the strategy supplied a `RegionShape.interface_halfplane`:

- **`flow_restricted` (Byrd-class) — clip at the grounding line.** `process_flow_restricted` returns a `_interface_halfplane`: a half-plane polygon covering the *downstream* side of the (flow-filtered, resampled) grounding line — its straight edge follows the GL points ordered across-flow and extended well past both ends, offset far downstream. `build_regions` clips `grounded_polygon = grounded_polygon.difference(halfplane)` and `floating_polygon = floating_polygon.intersection(halfplane)` (each reduced to its dominant piece via `_dominant_polygon`). Since the grounding line *is* the physical grounded/floating interface, this removes the overlap by construction and gives a clean shared boundary: grounded ends at the GL as a smooth truncated tongue, floating begins there. This replaced an earlier `grounded.difference(floating_polygon)` step that carved a U-shaped bite out of the grounded region (grounded arms wrapping around the floating corridor's upstream protrusion) and left the floating corridor's raw landward corners exposed — confirmed for Byrd (see HANDOFF.md's interface-clip item). A small residual: the floating corridor's raw landward edge, where it sits downstream of the clip line beyond the fast-trunk GL's own lateral extent, can leave a couple of ~2-3km spikes near the interface.
- **`simple` (Amery-class) — shrink grounded.** No single flow-defined interface exists (the regions meet along the whole-shelf boundary), so `RegionShape.interface_halfplane` is `None` and `build_regions` falls back to `grounded_polygon = grounded_polygon.difference(floating_polygon)` (dominant piece kept). `floating_polygon` is authoritative in any overlap — its post-smoothing shape is the one specifically fixed and GL-aligned for this area (the reverse direction was tried first and reintroduced the GL-misalignment bug the protection-radius fix above solves). A near-no-op for Amery (negligible overlap), held byte-identical by `tests/regression_baseline.py`.

`utils/raster_utils.boundary_sharpness`/`sharpest_points` (rasterize a polygon, Laplacian-of-Gaussian filter over its distance-to-boundary field, restricted to near-boundary pixels to avoid a shape's medial axis confounding the result) is a general-purpose diagnostic for exactly this kind of "is this transition unphysically sharp" question — used to root-cause the `grounded_polygon`/floating-corridor width mismatch above via a grid search that ruled out every floating-side taper parameter before finding the real cause on the grounded side. Not wired into the build itself; a standalone tool for this kind of geometry debugging.

The calving front is then loaded and immediately passed through `_trim_front_to_region` — `calving_front.load_calving_front`'s providers accept a `region_polygon` argument but none reference it in their body, so they always crop from the *named shelf's* full extent regardless of `floating_polygon`; once that's a restricted corridor, front points from elsewhere on the shelf need to be dropped explicitly. When `front_reference_points` is available (`flowline_corridor`), they restrict *which part* of `floating_polygon.boundary` counts as a valid match, rather than being matched against directly as a sparse point set: `_FRONT_EXIT_BUFFER_M=20000m` around the ~24 exit points, intersected with `floating_polygon.boundary`, gives a continuous reference along the real front-facing arc between them (matching against the sparse points directly left the vast majority of a real front classified as generic cut boundary instead — confirmed for Byrd, median exit-point-to-real-front distance ~8km, tail past 40km, both far more than a `step_m`-scale tolerance assumes). The standard `_FRONT_REGION_TOLERANCE_M=8000m` (needed for the whole-shelf case — confirmed up to 5583m for Amery) is then safe to use against this restricted geometry — unrestricted, that same tolerance bleeds through the corridor's lateral `margin_km`-wide edges and pulls in front points from an unrelated stretch of coastline (confirmed for Byrd). `whole_shelf`/`basin_partition` fall back to the same tolerance against the full (unrestricted) `floating_polygon.boundary` (no `front_reference_points`).

`build_regions` then calls `_reconcile_front_with_velocity`, which compares the configured calving front against the boundary implied by the velocity data's own valid-coverage edge (`calving_front_source="velocity_mask"`) — front and velocity products are essentially never from the same epoch (see the front-conformance-misfit item in `HANDOFF.md`) — and, on a systematic (>500m median) disagreement, warns and resolves it one of two ways: if the configured front lies ocean-ward of real velocity coverage, `floating_polygon` is eroded inward to stop at the real data extent; if it lies landward instead (the case observed for Amery), the polygon is left alone and `DomainRegions.erode_velocity_beyond_front` is set so `build_dataset._build_region` drops floating-region velocity points seaward of the front once loaded (`build_dataset._filter_by_front`).

`build_regions` then extends `floating_polygon` to actually reach every (already-trimmed) front point it's reporting as its own: `_trim_front_to_region`'s tolerance (`_FRONT_REGION_TOLERANCE_M=8000m`) already treats a front point up to that far from `floating_polygon`'s boundary as belonging to the region — a real digitization mismatch between two independently-built edges (confirmed for Amery's `whole_shelf` case, median 1360m/max 5583m; for Byrd's `flowline_corridor` case, median 3675m/max 7910m — a buffered-streamline corridor's terminus is naturally narrower/rounder than the true, wider calving front). Trusting those points as the front but leaving the polygon short of them left a visible gap between the front markers and the region's own edge. `build_regions` unions a buffer of that same tolerance around the kept front points into `floating_polygon` (no re-intersection against `shelf_raw`/`grounded_polygon` — the polygon can already legitimately extend past that raw bound from earlier closings, e.g. `_clean_floating_polygon`'s ~476 km² inflation for Amery, and front points sit hundreds of km from `grounded_polygon` so there's no realistic risk of reaching it).

Finally, `build_regions` returns `DomainRegions` — `grounded_polygon`/`floating_polygon`/`grounding_line`/`calving_front`/`calving_front_normals`/`erode_velocity_beyond_front`, nothing about Dirichlet boundaries. That's computed downstream, in `build_dataset._build_region`, from the *velocity data's own mask*, not from either region polygon's geometric ring: `_accepted_velocity_mask` builds a raster of exactly which MEaSURES pixels are accepted into that region's `xd/yd/ud/vd` (`CNT>0`, inside the polygon, and the same region-specific filter applied to the point cloud — `grounded_min_speed_myr`'s threshold for the grounded region, the front-seaward exclusion for the floating region when `erode_velocity_beyond_front` is set), and `_dirichlet_from_mask` (`utils.raster_utils.boundary_indices`) finds the true pixel-adjacency edge of that exact accepted set, excluding pixels within `gl_exclusion_km` of the grounding line (and, for the floating region, the calving front) since those are reported physical interfaces (`x_md/y_md`, `xct/yct`) in their own right. This replaced an earlier, shallower approach (`domain._cut_boundary` + `build_dataset._dirichlet_from_boundary`) that derived a "cut boundary" from the region polygon's own geometric ring and then nearest-neighbor-matched real velocity within a fixed search radius — a proxy that can diverge substantially from where the accepted-data mask actually ends: confirmed for Byrd, the velocity-thresholded grounded corridor's own polygon edge sits up to `corridor_margin_km` beyond the real fast-flow contour it's traced from, in ice often genuinely slower than `grounded_min_speed_myr`, so the ring-based proxy found real *accepted* velocity near only ~11% of its own candidate points (33/307) even though 100% had real *unfiltered* velocity nearby. The mask-boundary approach also naturally finds real interior data gaps a polygon-ring proxy could never see at all — confirmed for Amery: a genuine ~20km InSAR coverage gap inside the floating region (likely an ice rise) now gets its own Dirichlet ring, previously invisible to the ring-based approach entirely.

`build_dataset.build_dataset(config)` then loads velocity/thickness/surface per region against these polygons, resamples the dense thickness and dense surface sources onto the velocity grid via nearest-neighbor (`resample.py` — needed because different sources live on different native grids) to get `h_dense`/`s_dense`, keeps sparse thickness and sparse surface at each one's own native points (`xd_h`/`yd_h`/`hd` and `xd_s`/`yd_s`/`sd` respectively — no resampling between them, see the ADR above), computes `ols_d` as geometric signed distance to the grounding line (not a levelset PDE solution), and assembles the final two-region dict.

### Diagnostics are separate from the build

`diagnostics/plot_validation.py` (visualize a built `.mat`'s regions/collocation/thickness/velocity), `diagnostics/compare_sources.py` (overlay + nearest-neighbor stats between alternative GL/front sources for the same shelf), `diagnostics/checks.py` (CLI over the `checks/` registry — one subcommand per registered check), and `diagnostics/plot_basins.py` (plot every named drainage basin and check whether ice shelves are partitioned along the same boundaries) are standalone CLIs, not part of `build_dataset`. Run them after building to sanity-check a domain before trusting it for training. `utils/color_utils.py` is a small shared helper (`distinct_colors`) used by these plotting scripts.

### `utils/basin_partition.py` is experimental and not wired into the build

Labels every point on an ice shelf by which grounded drainage basin's flow dominates there, since the `iceshelves_2008_v2.mat` polygons aren't partitioned along basin boundaries. Method: seed forward streamlines on real flux-gate pixels (BedMachine grounded/floating adjacency, filtered to genuine inward flow), integrate them across the shelf, and nearest-neighbor-label every shelf point against the combined path cloud. Run standalone via `python -m joint_xpinn_data.utils.basin_partition --ice-shelf Amery`; read its module docstring before changing the method — it replaced an earlier backward-tracing design that used shared-boundary length as a heuristic and got Amery's basin attribution wrong. See `HANDOFF.md` for its known limitations and whether/how it should eventually feed into `build_dataset`. It lives in `utils/` alongside the shared-helper modules rather than a dedicated "experimental" package (a deliberate choice — it's the only module of its kind, not worth a whole package for one file), even though, unlike the other `utils/` modules, it's a standalone CLI tool nothing else imports.
