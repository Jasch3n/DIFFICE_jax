# Handoff notes

Status: the core pipeline builds and validates end-to-end for Amery/Lambert (`buffer_km=10` and `100` both tested), and Amery/Mellor and Amery/Fisher build successfully too (visually spot-checked, not run through the full `compare_sources`/`checks` battery — see "Natural next steps"). DIFFICE_jax has since been patched to accept this pipeline's independently-coordinated surface elevation output (`xd_s`/`yd_s` — see `docs/adr/0001-*.md`), so the schema-compatibility blocker is resolved; an actual DIFFICE_jax training run against this pipeline's output is still the next real validation this needs. A separate experimental tool (`utils/basin_partition.py`) now also produces a complete, physically-sensible per-basin province labeling of Amery's shelf, but isn't wired into the main build.

The codebase went through a reorganization pass (file layout: `checks/`/`utils/`/`diagnostics/` packages, per-config `output/<stem>/` folders; a new independent `surface` data kind fixing a latent `sd` bug; a `checks` registry generalizing the one-off conformance check) — see root `CLAUDE.md` for the current architecture and `CONTEXT.md`/`docs/adr/0001-*.md` for the vocabulary and the one deliberate schema deviation this introduced.

## What's implemented

- Config-driven domain construction (`ice_shelf`, `grounding_zone`, `buffer_km` → two region polygons) — see root `CLAUDE.md` for the architecture summary.
- Pluggable providers for velocity, thickness (dense + sparse roles), surface elevation (dense + sparse roles, independent of thickness), grounding line, calving front — each a registry entry, see `WORKFLOW.md` §2 for the config surface. Three independent calving-front sources exist (`bedmachine_mask` default, `antarctic_boundaries_mask`, `velocity_mask`) plus two grounding-line sources (`measures_boundaries_2008` default, `bedmachine_mask`) — `diagnostics/compare_sources.py` cross-checks any pair.
- `.mat` output matching DIFFICE_jax's synthetic-data schema, plus one deliberate addition (`xd_s`/`yd_s` for surface elevation's own coordinates — see `docs/adr/0001-surface-elevation-independent-coordinates.md`). `expected_save_variables` reflects the addition.
- Validation tooling: `diagnostics/plot_validation.py` (visualize a built `.mat`), `diagnostics/compare_sources.py` (overlay + nearest-neighbor stats between alternative GL/front sources), `diagnostics/checks.py` (CLI over the `checks` registry — `velocity_vs_front`: strict conformance check, flags valid velocity measurements on the open-ocean side of the mapped calving front; `hydrostatic_equilibrium`: descriptive flotation-residual check between thickness and surface elevation in the floating region).
- YAML config files (`configs/*.yaml`, loaded via `config.load_config`) + a CLI on `build_dataset.py` — `python -m joint_xpinn_data.build_dataset <file.yaml or configs-dir>`. Unknown fields in a YAML raise a clear error listing valid `PipelineConfig` fields; a `paths:` block in the YAML merges into `DEFAULT_PATHS` rather than replacing it.
- `PipelineConfig.grounded_min_speed_myr` (default `None` = no filtering): drops grounded-region velocity points at or below this speed, and everything resampled/derived from them (`xd`/`yd`/`ud`/`vd`, `xcol`/`ycol`, `h_dense`/`s_dense`, `ols_d`) — see `build_dataset._filter_by_speed`. Floating region is never filtered this way. All three Amery configs set this to `100.0` (excludes near-stagnant ice, e.g. near an ice divide, from the grounded region's training data); for Amery/Lambert this removes one small interior gap's worth of points but otherwise leaves the grounded region intact (Lambert is a fast-flowing trunk almost everywhere in the 100km buffer).
- `PipelineConfig.grounding_line_resample_m` (default `None` = keep native vertex spacing): artificially resamples the grounding line to an even arc-length spacing via linear interpolation (`utils/geometry_utils.resample_polyline`/`resample_geometry`) before it's used anywhere — corridor buffer, cut boundary, `ols_d`, `x_md`/`y_md`. All three Amery configs now set this to `500.0`, guaranteeing no two consecutive `x_md`/`y_md` points are more than 500m apart (verified directly: max consecutive spacing 493-500m for Lambert/Mellor/Fisher, vs. `measures_boundaries_2008`'s native 54/24/23-point resolution). `Geometry.ordered` (new `contracts.py` field, default `True`) records whether a source is a genuine walkable polyline; `resample_geometry` checks it and, for an unordered mask-pixel-adjacency source (`bedmachine_mask`, explicitly marked `ordered=False`), emits a loud multi-line `UNORDERED GEOMETRY IS BEING RESAMPLED` warning and falls back to `order_counterclockwise` (sort by polar angle around the centroid) before interpolating — a heuristic exact only for a star-shaped point cloud, not a real boundary reconstruction. Verified this warning fires for `bedmachine_mask` and stays silent for the real Amery configs (all use the ordered default source).
- `diagnostics/plot_basins.py`: plots all 199 refined basins (labeled) and overlays ice-shelf outlines on them — confirms ice shelves are NOT partitioned along basin boundaries (83/181 shelves are fed by 2+ basins). `python -m joint_xpinn_data.diagnostics.plot_basins`.
- `utils/basin_partition.py` (see its own section below): labels every point on a shelf by which drainage basin's flow dominates there. Its `flux_gate_seeds`/`velocity_field`/`trace_forward_paths`/`partition_shelf` are now also reused (unmodified) by `floating_region.py` — see the next bullet — so it's no longer purely a standalone diagnostic; its `DEFAULT_PATHS`-hardcoding was fixed (threaded an optional `paths` param through, matching `config.path(...)`'s pattern) so a config's `paths:` override is honored there too.
- **New `floating_region.py` registry** (`PipelineConfig.floating_region_source`/`floating_region_kwargs`) controls how far the floating region extends beyond the grounded corridor — `whole_shelf` (default, exactly the prior-only behavior: the named shelf's full extent minus the grounded corridor, independent of `buffer_km`/`grounding_zone`); `flowline_corridor` (traces forward streamlines from just the chosen `grounding_zone`'s own flux-gate seeds, buffers by `margin_km`, intersects with the whole shelf — cheap, reuses `basin_partition.flux_gate_seeds`/`trace_forward_paths`); `basin_partition` (runs the full multi-basin `basin_partition.partition_shelf`, keeps only the chosen zone's labeled points, buffers by `margin_km` — more principled competition against every real contributing basin, more expensive). Built for Ross East/Byrd (see below) — restricting to a single tributary's corridor on a shelf as large as Ross East (fed by many outlet glaciers) avoids a floating region that's ~99% unrelated shelf plain. Both corridor strategies warn loudly if the result has interior holes or multiple disconnected components with no dominant one (a fixed `margin_km` bounds gaps *along* one streamline but not *across* diverging ones).
  - Restricting the floating region exposed two things needing separate handling, both now fixed as part of this: (1) `calving_front.load_calving_front`'s providers accept a `region_polygon` argument but none reference it in their body (confirmed via grep) — so `xct`/`yct` needed an explicit post-hoc trim to the restricted region (`domain._trim_front_to_region`, plain pointwise filter, tolerance `_FRONT_REGION_TOLERANCE_M=8000.0` — see the empirical basis in domain.py's comment, needed because independently-digitized products describing "the same" seaward edge disagree by several km even for the *whole* shelf); (2) `domain._cut_boundary` (previously grounded-region-only) was generalized to take a list of exclusion geometries and applied to the floating region too — which surfaced bug #7 below, a real completeness gap in every existing Amery config, not something specific to the restriction work.
- A second BEDMAP-series thickness source, `bedmap2_csv` (BGR's 2002-2003 PCMEGA airborne radar survey, Lambert Glacier/Prince Charles Mountains), plus a `concat` pseudo-source (`data_sources/thickness.py`, any thickness role) that merges multiple named sources into one `PointObservations`. All three Amery configs now set `sparse_thickness_source: concat` combining `bedmap1_csv` + `bedmap2_csv` (88,697 floating-region points for Amery/Lambert, vs. 69,351 from BEDMAP1 alone) — PCMEGA fills real coverage gaps BEDMAP1 leaves in this specific area. `bedmap1_csv`'s column-reading internals were generalized (`process_bedmap1_column` → `process_bedmap_column`, `_read_bedmap1_csv` → `_read_bedmap_csv`, `_BEDMAP1_*` constants → `_BEDMAP_*`) since BEDMAP1 and BEDMAP2's CSV exports share the exact same column names/-9999 sentinel convention; `surface.py`'s BEDMAP1 surface provider was updated to match (no BEDMAP2 surface source added — PCMEGA's `surface_altitude` column exists in the file but wasn't asked for).

## `utils/basin_partition.py` in detail

Its per-basin building blocks (`flux_gate_seeds`, `velocity_field`, `trace_forward_paths`, `partition_shelf`) are now reused by `floating_region.py` (see above) — no longer purely standalone. It's still also runnable on its own as a shelf-wide diagnostic: `python -m joint_xpinn_data.utils.basin_partition --ice-shelf Amery`. Read its module docstring before changing it; the method went through several iterations, each fixing a real problem with the last, and the docstring explains why the current approach looks the way it does.

**Current method**: for each basin touching the shelf, find the actual grounded/floating interface pixels (BedMachine mask adjacency), keep only pixels with measured positive inward flow (velocity component along the outward normal), and use those as forward-tracing seeds — "close to the grounding line but still grounded." Trace each seed forward (with the flow, arc-length-parametrized RK4) until it leaves the shelf polygon, recording the whole path. Label every shelf point by nearest-neighbor lookup against the combined cloud of all basins' path points.

**Result for Amery**: 100% of all 299,495 shelf points classified (no subsampling needed, full resolution runs in ~30s), median distance-to-nearest-streamline 0.5km, max 10.4km, with a clean physically-coherent lateral stratification across all 5 real contributing basins (American HighLand, Lambert, Mellor, Fisher, MacRobertson Land, arranged south-to-north exactly as expected from known glaciology).

**How it got there — two earlier designs, both instructive:**
1. *Backward tracing from every shelf point.* Integrate each shelf point backward (against the flow) until it re-enters some basin polygon. Required filtering candidate basins first, by shared-boundary *length* (short arc = real tributary, long arc = assumed lateral rock wall). That heuristic was **wrong**: `MacRobertson Land` and `American HighLand` (long shared boundaries) turned out to have the 1st- and 3rd-highest real inward flux of any basin touching Amery (confirmed both are 98%+ grounded ice via BedMachine mask, not rock — checked directly), while `Mawson Coast` and `Publications` (short shared boundaries, assumed real tributaries) turned out to have *zero* actual grounded/floating interface pixels — no physical connection at all. This fully explained an earlier finding that backward-traced points were spuriously landing in `Mawson Coast` despite being 33-407km from its only possible (nonexistent) entry point. Separately, Euler integration was replaced with RK4 (Euler cut corners into the wrong basin polygon in curved flow) and the velocity field needed Gaussian smoothing before integration (pixel noise faked closed streamlines that trapped a trajectory regardless of step budget — confirmed by doubling the step budget and seeing zero improvement). Even after both fixes, only ~55% of points resolved.
2. *Forward tracing from flux-gate seeds (current).* Seeding directly on measured flux makes basin selection self-correcting — a basin with no real interface contributes zero seeds automatically, no separate filter needed. `basin_shelf_flux` (net flux between any basin/shelf pair) remains as a standalone diagnostic.

**What's not yet done here**: only tested on Amery — not run on any other shelf. A couple of small ring/loop artifacts appear in the plot (thin `Islands`-colored loops cutting through the `American HighLand` band); `Islands` is a scattered-island basin with small, mixed-sign net flux, so its few surviving seeds may trace oddly — not investigated further. `min_normal_velocity_myr` (the per-pixel seed threshold, default 0.0 = any positive inflow) hasn't been tuned or sensitivity-tested. If this output is going to feed into anything real (e.g. an extra per-point province label in `build_dataset`'s output), start with testing on another shelf and looking into the `Islands` artifact.

## Bugs found and fixed during development (context for why some code looks the way it does)

1. **Ice-shelf/basin polygons have holes.** `boundaries._rings_to_polygon` originally unioned every ring as solid fill; Amery's shapefile-derived polygon has 7 interior holes (ice rises/rock) encoded via ESRI winding order. Fixed by classifying rings via signed area. If a *new* boundaries source is ever added, check whether it needs the same treatment.
2. **`scipy.io.loadmat(..., simplify_cells=True)` returns MATLAB cells as object-dtype `ndarray`, not `list`.** `plot_validation._as_cells` originally only checked `isinstance(value, list)`, silently collapsing both regions into one blob. Any new code reading these `.mat` files needs the same dtype check, not just an `isinstance(list)` check.
3. **The old `measures_boundaries_2008` calving-front method is structurally wrong for multi-tributary shelves.** It only excludes the boundary arc near the *one* grounding line passed in, so any other tributary's grounding-line-adjacent arc (or plain rock coastline) gets misclassified as open-ocean front. This is why `bedmachine_mask` (real mask-transition lookup) is now the default — it's correct by construction regardless of how many tributaries feed the shelf. `measures_boundaries_2008` is kept only as a fallback for shelves with a genuinely single grounding zone or no gridded mask available.
4. **`sd` (surface elevation at the sparse-thickness role) was silently aliased to `s_dense`.** `build_dataset._build_region` set `sd = s_dense` — the *dense*-role surface value resampled onto the velocity grid (`xd`/`yd`) — even though the schema documents `sd` as living at `xd_h`/`yd_h` (the *sparse* role's own points, same as `hd`). The two have different lengths for a real config (e.g. 69349 vs 69351 for Amery/Lambert's floating region), so this wasn't just a naming slip. Fixed by giving surface elevation its own independent data kind (`data_sources/surface.py`) with a real sparse-role provider (BEDMAP1's `surface_altitude` column) — see `docs/adr/0001-surface-elevation-independent-coordinates.md` for why the fix also gave `sd` its own coordinates (`xd_s`/`yd_s`) rather than resampling it onto `xd_h`/`yd_h`.
5. **Mask-based GL/calving-front providers cropped to a bounding box, not the actual named polygon, so `xct`/`yct` could include points nowhere near the shelf they're supposed to describe.** `calving_front.process_bedmachine_mask` (the default `calving_front_source`) crops BedMachine's mask to `shelf_poly.bounds` (padded), then takes *every* floating_ice/ocean transition in that crop as calving front — with no check that the floating ice on either side of a given transition is actually part of the named shelf. For Amery/Lambert this silently included ~85 points (of 1000) from an unrelated ice mass ~55-59km outside Amery's polygon that happened to share the padded bounding box, plus a handful of smaller 2-19 point fragments (found via connected-component analysis of the raw `is_shelf` mask: the true shelf is one 242,558-pixel blob in the crop, vs. an 784-pixel second-largest blob for the unrelated fragment and everything else under 55 pixels). Fixed by `utils.raster_utils.largest_connected_component`: label the boolean category mask (`is_shelf`/`is_valid`) and keep only its largest connected component before extracting boundary points. Applied to all three raster-mask front providers (`process_bedmachine_mask`, `process_antarctic_boundaries_mask`, `process_velocity_mask`); `bedmachine_mask` (the one that actually feeds `xct`/`yct`) went from 1000 to 914 points for Amery/Lambert, all traceable to the real shelf. This is a different, additive fix from the pre-existing `velocity_vs_front` FAILED result below — that's real velocity data landing seaward of an otherwise-correct front (epoch mismatch); this was front points that were never really "the front" at all.
6. **`x_md`/`y_md` (grounding line) included points nowhere near where the grounded and floating regions actually touch — a pre-existing bug the `grounding_line_resample_m` work surfaced visually (denser interpolated dots made a small pre-existing offset an obvious trailing streak), but present even without resampling.** `grounding_line.process_measures_gl` (the default `measures_boundaries_2008` source) keeps continental grounding-line points within `tol_km` (default 10km) of the *basin's entire boundary ring* — which includes lateral basin walls shared with neighboring basins/rock, not just the ice-shelf-facing arc. Confirmed empirically for Amery: per-point distance from each raw returned segment to the true `grounded_polygon`/`floating_polygon` shared boundary is ~0m through the middle, then jumps straight to several km (up to ~10km) at both tail ends of the segment — those tails sit on a basin wall, not the interface. Worst for Mellor (median offset >2km across its whole 24-point segment). Fixed by `domain._trim_gl_to_interface`: after building `grounded_polygon`/`floating_polygon`, keep only GL points within 1km (`_GL_INTERFACE_TOLERANCE_M`) of their true shared boundary — by contiguous run for an ordered polyline source (drops the tails, keeps the middle), or pointwise for an unordered scatter source (no "run" concept applies). Applied before any resampling. Verified against the rebuilt `.mat`s: max distance-to-true-interface dropped from up to ~9975m to 0-991m (Lambert 0m, Fisher 56m, Mellor 991m — bounded by the 1km trim tolerance itself) across all three Amery configs.
7. **The floating region's `xdir`/`ydir`/`udir`/`vdir` were unconditionally empty, silently discarding a real physical boundary condition for every existing Amery config.** The pre-existing assumption (`build_dataset.py`'s old docstring: "the only real boundaries of the shelf are the grounding line and calving front") is false whenever a shelf is fed by more tributaries than a config models — confirmed via `utils/basin_partition.py`: Amery touches 6 basins (American HighLand, Fisher, Islands, Lambert, MacRobertson Land, Mellor), and every existing Amery config only models one as its grounded region, so most of the floating region's boundary is actually a real grounded/floating interface with one of the other 5. Discovered while generalizing `domain._cut_boundary` (previously grounded-region-only, needed for the new floating-region-restriction work below) to the floating region too: for Amery/Lambert this surfaces 4625 points (up to then silently zero) tracing the shelf's boundary with American HighLand/MacRobertson Land/Islands/Mellor/Fisher — visually confirmed correct (each config's own chosen zone's GL arc is properly excluded; the true calving front arc is also properly excluded). Fixed by giving this arc the same treatment the grounded region's own arbitrary buffer-radius truncation already gets: a data-driven Dirichlet BC (`build_dataset._build_region`'s floating branch, previously hardcoded `np.zeros(0)`). Verified this is additive, not a regression: `xd`/`xd_h`/`xct`/`x_md` counts are byte-identical to before this fix for all three Amery configs; only the previously-always-empty `xdir`/`ydir`/`udir`/`vdir` for the floating region changed.

8. **`utils.geometry_utils.circular_runs` (contiguous-True-run detection around a closed ring, used by `domain._cut_boundary` and `calving_front.process_measures_front`) silently mishandled wraparound when a ring has more than one excluded ("False") zone.** If a True run was still open when the main scan reached the ring's last index, the old code assumed it "wraps around" and grabbed exactly `len(ring)` points from a doubled array *without checking* that the wrapped portion was actually still True — for a ring with only one excluded zone this happens to give the right answer (there's nothing else nearby to wrongly include), which is why it went unnoticed for `grounded_polygon`'s cut boundary (GL is its only excluded zone) throughout this session's earlier work; `floating_polygon`'s ring (GL *and* calving front both excluded) was where it surfaced — see the Ross East/Byrd sharp-edge investigation below for how it was found and confirmed (a specific point 2.97m from a real GL point was present in `_cut_boundary`'s output despite its own ring index being correctly classified `far=False`). Fixed by rotating the ring to start immediately after a real False point before scanning, so a run can never need to reason about wrapping past the array boundary at all. Predates this session's other changes — `circular_runs` itself wasn't touched until this fix — so any single-shelf, single-exclusion-zone config (e.g. every existing Amery config's grounded region) was unaffected, but any use case with 2+ excluded zones on one ring should be treated as suspect if this fix is ever reverted.

## Known limitations / things not yet done

- **Hardcoded absolute path.** `config.DATA_ROOT = Path("/Users/jiapchen/Research/Data")` — not portable to another machine/user without editing this constant.
- **BedMachine's grid is read twice per region when `dense_thickness_source` and `dense_surface_source` are both `bedmachine_v3`** (the default for both) — once for `fields=("thickness","bed")`, once for `fields=("surface",)`, since surface elevation is deliberately an independent data kind (see `docs/adr/0001-*.md`) rather than reusing thickness's bundled read. The equivalent BEDMAP1 CSV double-read (thickness's and surface's sparse roles both defaulting to `bedmap1_csv`) is mitigated — `data_sources/thickness.py._read_bedmap1_csv` is `lru_cache`d so the ~1.9M-row file is parsed once per process regardless of how many roles/regions request it — but the BedMachine netCDF read isn't, since index-slicing a grid is already fast and caching it would need to be keyed on the region polygon, not just the file path. Not worth optimizing further unless it shows up as a real bottleneck.
- **`xcol`/`ycol` (collocation points) just reuse the velocity grid points** (`xcol, ycol = xd, yd` in `build_dataset._build_region`). No independent/denser collocation sampling has been implemented — worth revisiting since PINN physics-residual accuracy benefits from collocation density independent of data sparsity.
- **`ols_d` uses nearest-*vertex*-on-the-GL-point-cloud distance, not exact point-to-line distance.** For sparse grounding-line representations (e.g. `measures_boundaries_2008`'s native ~54-point Lambert segment), signed distance can overshoot the nominal buffer radius by a few km near vertices. Cosmetic today (not used in the physics residual) but worth fixing if `ols_d` becomes load-bearing. **Mitigated, not fixed**: all three Amery configs now set `grounding_line_resample_m: 500.0` (see above), which shrinks the worst-case overshoot to ~500m by densifying the vertex cloud — but it's still a nearest-vertex approximation, just a tighter one, not exact point-to-line distance.
- **BEDMAP1 sparse thickness (`hd`) has some exact-zero values** in both regions that survived the `-9999` sentinel filter — likely legitimate rock-outcrop/margin points, not investigated further. The new `hydrostatic_equilibrium` check's extreme outliers (delta up to ~1.85e6 kg/m^2 for Amery/Lambert's floating region, vs. a median of ~1.3e4) are plausibly the same points — not confirmed, worth cross-referencing before trusting the check's tails.
- **RESOLVED — the velocity/calving-front conformance misfit.** `diagnostics/checks.py velocity_vs_front` used to fail for Amery/Lambert: ~24-26.5% of near-front velocity points (within 5km) sat on the open-ocean side of the mapped `bedmachine_mask` front, in a systematic ~2-3km-wide band along nearly the whole front (not random noise) — see `output/Amery_Lambert_100km/figures/Amery_Lambert_velocity_vs_front.png`. Confirmed root cause: epoch mismatch, not InSAR sea-ice coherence — rerunning the check with each front source (`search_radius_km=5`, Amery/Lambert 100km) gave a clean epoch-ordered gradient in the seaward-misfit fraction: `bedmachine_mask` (2021 epoch) 26.5%, `antarctic_boundaries_mask` (2017 epoch) 3.65%, `velocity_mask` (self-referential — front derived from the velocity data's own coverage) 0.0% (trivial pass, as expected). Coherence dropout wouldn't produce this ordering; a shelf that calved/advanced between epochs would.
  - **Fix**: `domain.build_regions` now calls `_reconcile_front_with_velocity` after building `floating_polygon`, which compares the configured front against the `velocity_mask`-derived boundary and, on a systematic (>500m median) disagreement, warns (`warnings.warn`) and resolves it by direction — front ocean-ward of real velocity coverage → erode `floating_polygon` inward (shapely negative buffer, by the 95th-percentile overshoot distance) so the region never claims area with no velocity support; front landward of real velocity coverage (the case actually observed for Amery) → leave the polygon alone and set `DomainRegions.erode_velocity_beyond_front`, which `build_dataset._build_region` uses (`build_dataset._filter_by_front`) to drop floating-region velocity points seaward of the front once loaded, rather than trusting them as real floating-ice motion. Verified directly against `_build_region`'s output for Amery/Lambert: 0 of 295,924 floating-region velocity points now land seaward of the front (previously up to 26.5% of near-front points did). All three Amery configs rebuilt with this fix; `pyflakes` clean.
  - **Caveat**: `diagnostics/checks.py velocity_vs_front` run standalone will still report FAILED for `bedmachine_mask` — it deliberately re-queries velocity fresh in a disk around the configured front, independent of `build_regions`'s reconciliation, so it still surfaces the raw disagreement rather than the corrected build output. That's intentional (it's the diagnostic that *detects* the misfit); to see the fix's effect, inspect `_build_region`'s output directly or diff `xd`/`yd`/`ud`/`vd` counts in the `.mat` before/after, not the check CLI.
  - The `_FRONT_VELOCITY_TOLERANCE_M = 500.0` (domain.py) and `95th-percentile` erosion-magnitude choices are reasonable defaults, not empirically tuned — revisit if a shelf shows a much larger or much noisier front/velocity offset than Amery's.
- **`hydrostatic_equilibrium` has no default threshold.** For Amery/Lambert's floating region, `delta` has median ~1.28e4 kg/m^2 (roughly 12.5m of surface-elevation-equivalent, dividing by `rho_seawater` — plausibly consistent with the known firn-column effect the two-density formula doesn't model) but a heavy tail (p90 ~5.3e4, max ~1.85e6). Nobody has yet decided what residual is "acceptable" for this data — see `checks/hydrostatic.py`'s docstring.
- **`grounding_zone` only meaningfully changes the grounded region, not the floating one — confirmed by running Mellor/Fisher through `compare_sources` and both `checks`.** `iceshelves_2008_v2.mat`'s Amery polygon is already pure floating ice, so subtracting any one tributary's grounded corridor only clips a thin sliver near that grounding line; `floating_polygon`'s area/bounds come out identical (to floating-point precision) for Lambert/Mellor/Fisher. Consequently `velocity_vs_front` and `hydrostatic_equilibrium` (both floating-region-only) gave numerically identical results for Mellor and Fisher (and match Lambert's numbers reported above) — this isn't a scoping bug, it's a real structural property of `domain.build_regions`. The grounding-line half of `compare_sources` *does* differ per zone (Mellor: 24 GL points, mean 208m vs. `bedmachine_mask`; Fisher: 23 points, mean 204m), as does the front-vs-velocity-mask reconciliation warning (fires identically for all three since it's shelf-scoped, not zone-scoped, by the same logic). **Practical upshot**: Mellor/Fisher are now build-tested, visually spot-checked, and run through the full `compare_sources`/`checks` battery, but this doesn't actually exercise anything Lambert-specific for the floating-region checks — a genuinely different **ice shelf** (not just another Amery grounding zone) is needed to shake out assumptions the floating-region logic implicitly baked in from Amery. Other ice shelves entirely (anything in `iceshelves_2008_v2.mat` besides Amery) remain completely untested — the config surface should support them without code changes, but that's unverified.
- **No automated tests.** All verification so far has been manual (`pyflakes`, ad hoc scripts, visual inspection of PNGs, and cross-checking against known Amery geography/velocities). If this pipeline is going to be reused/extended, consider adding at least regression tests around `boundaries.get_named_polygon` (the hole-handling), `utils/raster_utils.mask_boundary_points` (the neighbor-adjacency math), and the `.mat` schema assembly.
- **`Mask_Antactica_v2.tif` is from Chad Greene's Antarctic Mapping Tools "Antarctic boundaries" toolbox** (values `0`=ocean, `125`=isiceshelf, `255`=isgrounded — confirmed empirically, not documented in any header/tag on the file itself; see `Antarctic-boundaries/README.md` for the function names this mirrors: `isiceshelf`, `isopenocean`, `isgrounded`).   - **A fifth bug, found by the user in what looked like the fully-fixed `plot_validation` figure: a small loop of cut-boundary points still appeared to circle part of the GL.** Numerically this was *not* another `circular_runs`-style misclassification (no cut-boundary point was within 2km of any `gl` point) — visually distinguishing `grounded_polygon`'s cut boundary from `floating_polygon`'s (plotted the same green color by `plot_validation`, both correct individually) revealed the real cause: `grounded_polygon` and `floating_polygon` actually **overlapped by ~216 km²**, so both regions' own (individually correct) cut boundaries traced around the same shared notch from opposite sides, looking like one connected loop. First fix attempt — `floating_polygon = floating_polygon.difference(grounded_polygon)` (treating `grounded_polygon` as authoritative in the overlap) — was backwards: it cut away the *smoothing floating_polygon needed to fix bug 3 in the first place*, reintroducing bug 1's ~26km GL misalignment on the floating side (confirmed directly). Correct direction, per explicit user correction: `grounded_polygon = grounded_polygon.difference(floating_polygon)` instead — `floating_polygon`'s post-smoothing shape is the one that's specifically been fixed and GL-aligned for this exact area, so it should be authoritative in the overlap, not `grounded_polygon`. Also drops any small disconnected fragment the subtraction slivers off (`grounded_polygon`'s own area dropped ~7%, 3036→2820 km² for Byrd — expected, not a bug) by keeping only the dominant piece directly, without another closing pass (which would just regrow part of the overlap). Verified with a full rebuild: overlap is back to ~0 (floating-point noise), both regions' `gl`-to-boundary alignment holds at ~450-513m, `grounded_polygon` stays a single smooth piece (no new jaggedness from the subtraction), Amery unaffected.

## Region-strategy refactor + grounding-line interface clip (later session)

- **`domain.build_regions` was split into a shelf-class strategy registry** (`REGION_STRATEGIES` = `process_simple` / `process_flow_restricted`, selected by `PipelineConfig.region_strategy`, default `"simple"`) — see `docs/adr/0002-shelf-class-region-strategy-registry.md`. Amery-class geometry (`simple`) and Byrd-class geometry (`flow_restricted`: GL flow-filtering, velocity-thresholded grounded corridor, near-interface smoothing) no longer share one `if config.X is not None`-branched function body; a shelf on the default path structurally cannot execute Byrd-class code. Byrd's config knobs moved into `region_strategy_kwargs` (`min_speed_myr`, `corridor_margin_km`); the former hand-synced `floating_region_kwargs.min_normal_velocity_myr` is now derived from `min_speed_myr` inside the strategy. Amery output held **byte-identical** across the whole refactor by the new `tests/regression_baseline.py` (the first code-correctness test in the repo — freezes `build_dataset`'s output for the three Amery configs and diffs a rebuild field-by-field; run `verify` after any shared-code change).
- **Four problems reported from inspecting the Ross East/Byrd `plot_validation` figures; two were stale-figure artifacts, two were real and are now fixed:**
  - **(stale) Calving front normals looping near the interface, and grounded non-GL boundary missing its Dirichlet points.** Both were already resolved in the current build — the pasted figures predated the rebuilds and `plot_validation` hadn't been re-run. Confirmed against the current `.mat`: floating front is 184 points all at the seaward edge (y ≈ −1.35e6, none near the interface), and the grounded region carries a full spread of `xdir/ydir` Dirichlet points along its truncation edge. **`plot_validation` does not auto-run after a build — always regenerate before trusting a figure.**
  - **(real) Grounded region had a U-shape with thin branches hugging the floating corridor's flanks; floating region had sharp corners near the interface.** Root cause (single, shared): both regions spilled across the grounding line — the grounded capsule (`buffer(gl, buffer_km) ∩ basin ∩ _grounded_corridor`) extends downstream past the GL, and `_smooth_near_interface` (inflationary) regrew the floating corridor upstream into it, a ~216 km² overlap lens straddling the GL. The old `grounded = grounded.difference(floating_polygon)` resolution (bug 5 above) carved that lens out of the grounded capsule, leaving a U/crescent with the floating protrusion's raw corners exposed. Confirmed by capturing the grounded polygon pre- vs post-subtraction: pre was a clean smooth capsule (3036 km²), post was a 10-piece shatter whose dominant piece (2820 km²) was the U.
  - **Fix: clip both regions at the grounding line instead of subtracting one from the other.** New `domain._interface_halfplane` builds a downstream half-plane whose straight edge follows the flow-filtered, resampled GL (points ordered across-flow, extended past both ends, offset far downstream); `process_flow_restricted` returns it as `RegionShape.interface_halfplane`, and the epilogue does `grounded = grounded.difference(halfplane)` / `floating = floating.intersection(halfplane)` (dominant piece each). The GL *is* the physical interface, so overlap → 0 by construction, grounded becomes a clean truncated tongue (U gone, confirmed visually and via the collocation figure — the leftward branch to x≈360k is gone), and the shared boundary follows the GL. `simple`/Amery has no single flow interface (regions meet along the whole-shelf boundary) so `interface_halfplane` is `None` and the old subtraction path is kept (byte-identical, per the regression harness). A **union-then-clip ("tiling") variant** was prototyped to also snap floating's landward edge to the clip line and remove the last spikes, but it produced 73 sliver holes (unioning two independently-digitized boundaries) — rejected as fragile; the intersection approach keeps the same ~8 negligible sub-0.03 km² holes as before.
  - **Residual floating landward "spikes" — traced to `_smooth_near_interface`'s GL protection, now also fixed.** Two thin ~2km inward slits near the interface (~8km from the GL) turned out to be introduced by the epilogue `_smooth_near_interface` itself: `fp_raw` (the `flowline_corridor` output) is smooth there, but the closing's GL-protection carve-out (a 10km buffer around the GL excluded from the smoothing zone) left a step where the protected raw zone abuts the smoothed zone. The protection only ever existed to keep floating aligned to the GL through the inflationary closing (bug 1) — but the interface clip now re-imposes that alignment exactly (GL-to-boundary ~11m mean with or without protection). So the epilogue now drops the protection (`protect_radius_m=0`) for the floating smoothing **whenever a strategy supplies an `interface_halfplane`** (i.e. `flow_restricted`), and keeps `_GL_PROTECTION_RADIUS_M` for `simple` (Amery, no clip). Verified: both slits gone, floating landward edge smooth, floating went from 8 tiny sub-0.03 km² holes to 0, GL alignment held, `grounded`/`floating` areas unchanged (2499 / 28336 km²), Amery byte-identical (`regression_baseline verify`). Only a ~500m data-resolution wiggle remains — not a corner.
  - **Sharp corner at the *end of the widening portion* of the floating corridor — fixed by making the corridor a uniform (constant) width, after two other approaches failed.** A distinct ~5km convex kink sat on the corridor's lower flank ~1035km south. Two attempts that did *not* work, both instructive:
    1. **Close-then-open edge smoothing** (`_smooth_corridor_edges`, `buffer +R,-2R,+R`): rounds convex bumps a plain closing can't, and did smooth the kink — but its opening (erosion) ate the narrow near-GL corridor neck, deleting a chunk of the floating region there. Reverted.
    2. **Changing the taper profile** (tanh → smoothstep `3t²-2t³`, so the width eases in at the GL and reaches a true plateau): implemented per request and kept as the better default profile, but proven a **no-op for Byrd** — the tanh and smoothstep corridors are byte-identical (symmetric difference 0.0 km²). The taper only shapes the buffer over the first `taper_km` (~15km) from the GL; the kink is far downstream where the buffer is already at full `margin_km` plateau in *both* profiles, and near the GL the shelf/grounded clip masks the radius difference entirely.
    - Root cause (diagnosed by plotting the corridor buffer envelope vs the `shelf.difference(grounded)` boundary): the kink is where the corridor edge *transitions* between the streamline-buffer envelope and the shelf-polygon boundary / a secondary flow lobe — an intersection corner, reached only because the wide 15km margin bulged far enough downstream to hit the shelf boundary. Confirmed the streamlines themselves are a coherent bundle that barely fans out, so the corridor's widening was almost all the 15km buffer, not flow divergence (`uniform 15km` has the *same* kink as the taper).
    - **Fix (per user suggestion): limit the corridor to a uniform, narrower width so there's no widening at all.** Set `floating_region_kwargs: {margin_km: 8.0, taper_km: 0.0}` for Byrd — `taper_km=0` makes `taper_margins_m` return a flat `margin_km` everywhere (no ramp), and 8km is narrow enough that the buffer never reaches the shelf boundary, so the corridor is a clean constant-width tube around Byrd's flow bundle with no fan-out and no kink. Config-only change (no code). Result: `floating` 28336 → 22631 km², one piece, 0 holes, overlap 0, front still 184 at the seaward edge, grounded unchanged; Amery byte-identical (uses `whole_shelf`, unaffected). `margin_km` is now the knob for how much shelf around the flow to include. A tiny notch remains where the corridor meets the interface clip — see the next bullet for why, and why it wasn't worth chasing further.
  - **The interface-clip "seam notch" — root-caused, found to be a real continuous bend (not a bug/kink), fix attempt gave marginal/inconsistent results, not applied.** Investigated at the user's request. First finding: `_interface_halfplane`'s "half-plane" edge (`spine`, domain.py) is not actually straight — it's a polyline threading through every real GL point in across-flow order. That's invisible for `grounded` (a wide capsule that fully dominates near the spine, so its cut edge just reproduces the spine/GL exactly — desired), but for the narrow (8km) floating corridor, `floating.intersection(halfplane)` is a `min(corridor_edge, spine)`-type construction: two independently-built curves (the corridor's own smooth buffered-streamline envelope, and the raw-GL-following spine) that must cross somewhere, and any two curves crossing at a shallow angle produce a locally tight bend right at the crossing.
    - Considered fitting the spine as a single straight line (least-squares/PCA through the GL points) instead: rejected — measured the GL's real shape in the local (across-flow, along-flow) frame and found a genuine ~13km along-flow S-curve within a 16.5km across-flow span (comparable amplitude to width, not a small perturbation) — a real geographic feature (likely the confluence narrowing), not digitization noise. A straight-line spine would discard it and misalign the clip from the true GL by up to that ~13km, reopening the exact GL-misalignment problem the interface clip exists to fix.
    - Measured the bend's actual character properly (broad-window, ~2km, tangent-direction curvature along the true contiguous boundary run — a naive bounding-box-then-sort approach falsely bridged two disjoint arcs of the ring into a fake straight chord, an instructive diagnostic mistake worth flagging for future geometry debugging: always check `np.diff(idx)==1` before treating a filtered index set as path-ordered). Result: the tangent angle changes *continuously* (no jump) — this is a real, moderate ~2-3km-radius-of-curvature bend, not a discontinuous kink. Max turning rate ~26°/km over the transition.
    - Tried smoothing the spine (Gaussian kernel in the local frame, mirror-padded to avoid boundary-flattening bias) at several bandwidths, to see if a smoother clip line reduces the bend: bw=1500m made it *worse* (36°/km); bw=2500-4000m gave only a modest, plateauing improvement (24.4°/km, ~8% better). Non-monotonic and marginal — not a reliable fix, and not worth the added complexity (a new smoothing parameter, another thing to keep in sync with `margin_km`) for an 8% change. Not applied; `_interface_halfplane`'s spine is unchanged (still the raw GL polyline).
    - **Conclusion: this is an inherent, real consequence of clipping a corridor narrower than the true GL's own along-flow variation against that GL's real shape — not a bug.** The GL itself genuinely curves by more than the corridor's width at this location; some bend where the corridor accommodates that is unavoidable without a fundamentally different construction (e.g. blending the two curves with an explicit weighted transition, rather than a hard intersection) — a bigger, riskier change than its cosmetic payoff justifies right now. Left as-is.
